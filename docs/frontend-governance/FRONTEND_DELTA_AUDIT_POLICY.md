# Frontend Delta Audit Policy

Status: `GOVERNANCE_SPECIFICATION`

## 1. Audit objective

The independent Delta Audit answers one binary question:

> Does this exact Frontend Candidate implement only the approved change, preserve all unaffected
> baseline semantics, and pass every regression required by the actual risk surface?

The audit is performed after Candidate self-validation. It is neither a design review nor a rerun of
only the implementer's preferred tests.

## 2. Independence

The audit owner must be identifiable and must not be the sole implementer of the material delta. The
auditor independently obtains or verifies:

- baseline and Candidate source/fingerprints;
- reference and contract versions/hashes;
- changed-file inventory;
- runtime/build artifact identity;
- test selection and raw evidence;
- Scene and interaction inventories.

The auditor may accept reproducible test evidence generated by others but must verify its exact
Candidate applicability. A prose summary or screenshot without build/SHA binding is insufficient.

## 3. Entry criteria

Do not start a decision audit until all are available:

1. approved Change Request revision;
2. current Approved Frontend Baseline manifest;
3. immutable Candidate SHA, clean source tree, and tree fingerprint for a decision audit;
4. exact baseline and Candidate build fingerprints;
5. explicit UX Reference version/hash for both sides;
6. product/backend contract coordinates;
7. six-Scene classifications;
8. baseline/Candidate interaction inventories;
9. required regression plan and raw results;
10. known limitations and Demo/real mode declarations.

Missing entry evidence yields `FAIL` for a release decision or `NOT_READY_FOR_AUDIT` before the
decision begins. It never yields a conditional pass.

## 4. Audit method

### Step 1 — Authenticate inputs

Verify full SHAs, clean-tree state or complete dirty fingerprint, lockfile, build command, build
artifact hash, reference hashes, test environment, browser versions, and evidence timestamps. Check
that tests ran against the same bits proposed for promotion.

### Step 2 — Establish the three-way comparison

Compare:

```text
Approved Baseline -> actual Candidate delta
Approved Change Request -> authorized intended delta
Applicable UX/Product/Backend references -> required semantic result
```

The Candidate passes only when the actual delta is fully explained by the request and agrees with
the applicable references. Generated files, configuration, dependencies, assets, routes, fixtures,
and test-oracle changes are part of the delta.

### Step 3 — Reconcile reference versions

Record both pairs:

```text
baseline frontend <-> baseline UX Reference
candidate frontend <-> candidate UX Reference
```

If the Candidate is compared to a superseded or mismatched reference, record
`REFERENCE_MISMATCH` and fail unless an approved compatibility declaration explicitly makes that
comparison the intended audit. See `FRONTEND_REFERENCE_VERSIONING.md`.

### Step 4 — Validate classification and reachability

Inspect actual changed modules and their reachable consumers. Confirm all applicable change types
were declared. Add missed pages, components, contracts, controls, or Scenes to the audit scope and
record the Change Request defect.

### Step 5 — Audit required regressions

Use the union matrix below. A selected type never removes another type's tests.

| Change type | Required audit path | Required adjacent/cross-cutting coverage |
|---|---|---|
| `UX_VISUAL` | affected page/state reference comparison at governed viewports | responsive reflow, zoom/content loss, contrast/semantics, loading/empty/error/disabled states |
| `INTERACTION` | affected control contract and complete affected journeys | keyboard/pointer, focus restore/trap, history/refresh, repeated action/idempotency, negative states |
| `BACKEND_CONTRACT` | adapter -> projection -> reducer/store -> page | unknown enums, optional/missing/error data, identity substitution, HTTP/SSE/reconnect as applicable |
| `PRODUCT_SEMANTIC` | Scenario Spec -> contract -> UI -> acceptance | safe claims, authority boundaries, A/B/C/Claim/Run/Object meaning, all affected Scenes |
| `ACCESSIBILITY` | semantic and manual interaction checks for affected surface | name/role/value, keyboard, focus order, announcements, contrast, motion at responsive variants |
| `RESPONSIVE` | all affected states at every governed viewport class | touch target, overflow, orientation, zoom, reading order, overlay behavior |
| `BUG_FIX` | reproduce-before/fail and Candidate/pass test | nearest sibling states plus every underlying change-type scope |
| `SCENARIO_CHANGE` | full affected Scene with new versioned oracle | shared gates, fixture/provenance truth, interaction mappings, prior-Scene compatibility or explicit supersession |

Pure visual changes therefore always cover affected pages plus responsive and accessibility checks.
Interaction changes cover affected controls plus journeys. Contract changes cover the complete
adapter-to-page chain. Product-semantic changes cover the complete Scenario-to-acceptance chain.

### Step 6 — Audit the six Scenes

For each of `SCENE-01..06`, verify the Change Request classification and actual reachability:

| Field | Allowed value |
|---|---|
| `scene_id` | stable Scene ID |
| `impact` | `AFFECTED` or `UNAFFECTED` |
| `reason` | specific contract/page/control/data rationale |
| `scene_version_before` | exact version/hash |
| `scene_version_after` | exact version/hash; same if unaffected |
| `required_gates` | Scene and shared gate IDs |
| `result` | `PASS`, `FAIL`, `NOT_RUN`, or `BLOCKED` |
| `evidence` | immutable evidence locator/hash |

Every affected Scene must pass in full, plus shared cross-cutting gates. `UNAFFECTED` is rejected if
the actual delta reaches any Scene setup, data, step, control, contract, result, or claim.

For Phase 4 integration, use the mappings and shared gates in
`../integration/PHASE4_BROWSER_SCENARIO_MATRIX.md`. A Demo Scene pass cannot substitute for its
required real-backend pass.

### Step 7 — Audit interaction contracts

Start from the baseline matrix, initially the 64 stable rows corresponding to
`P4-E2E-001..064`. Build a union inventory of baseline and Candidate controls. Each row must be
exactly `ADDED`, `REMOVED`, `CHANGED`, or `UNCHANGED`.

Audit rules:

- `ADDED`: new monotonic ID, contract text, accessible behavior, responsive behavior, affected
  Scenes, and passing tests are required.
- `REMOVED`: ID remains as a tombstone; explicit product-semantic approval, journey update, and
  alternative/no-longer-needed rationale are required.
- `CHANGED`: preserve ID, increment row/matrix version, show before/after behavior, and pass old
  non-superseded plus new expectations.
- `UNCHANGED`: verify actual contract equivalence; a source file being unchanged is not enough if a
  dependency, CSS rule, route, projection, or parent behavior affects the control.

Required totals:

```text
union inventory classified = 100%
Candidate exposed-control inventory classified = 100%
required interaction tests passed = 100%
```

Any unclassified exposed control, duplicated logical ID, reused retired ID, missing tombstone, or
untested changed contract is a release failure.

### Step 8 — Verify cross-cutting semantics

Regardless of focused scope, verify that the Candidate does not regress:

- exact Object/Run/Task/Claim/Review/Artifact/Execution identity boundaries where applicable;
- same-Run A/B/C and Claim Trace navigation;
- backend authority over runtime, financial values, review, and artifacts;
- Initial Plan versus Actual Path distinction;
- self-correction versus top-level Task semantics;
- Demo/FIXTURE/LIVE/PRE-INTEGRATION provenance labels;
- failure, loading, empty, disabled, unknown, and unavailable behavior;
- primary navigation, focus, responsive access, and accessible control exposure;
- artifact availability and refusal to fabricate an unavailable PDF or detail body.

### Step 9 — Account for every delta

The report includes a table with one row per material file/contract/behavior delta:

| Delta | Declared by change ID | Type | Expected | Observed | Tests | Finding |
|---|---|---|---|---|---|---|

Undeclared material changes fail until the request is amended and the required regressions run.
Unexpected absence of a declared change also fails because the Candidate does not implement its
approved request.

### Step 10 — Decide

The final result is exactly:

```text
audit_result: PASS | FAIL
```

`PASS` requires all mandatory evidence and tests. Informational observations may remain only when
they do not contradict an acceptance criterion, hide required work, or qualify the pass. There is no
`PASS_WITH_ISSUES` release state.

## 5. Finding severity

| Severity | Meaning | Promotion effect |
|---|---|---|
| `P0` | false authority/provenance, cross-identity exposure, security/safety failure, or unusable critical journey | fail |
| `P1` | approved product/interaction/contract/Scene/a11y/responsive semantic regression or missing required evidence | fail |
| `P2` | non-critical defect outside mandatory acceptance but requiring tracked correction | may pass only if it violates no required criterion and the approver explicitly accepts it |
| `P3` | editorial or non-behavioral observation | no automatic failure |

Severity does not override binary gates. A required test failure remains a failure regardless of
severity label.

## 6. Required audit report

The immutable audit record contains:

- `audit_id`, auditor, dates, and independence statement;
- `change_id` set and approved request revisions;
- baseline manifest/Frontend SHA/build hash/reference pair;
- Candidate SHA/tree fingerprint/build hash/reference pair;
- changed-file and dependency inventory;
- change-type reconciliation;
- page/component/contract reachability map;
- six-Scene impact/results table;
- complete interaction disposition table and coverage calculation;
- required-test planned/executed/pass/fail counts;
- environment and Demo/real classifications;
- material delta accounting table;
- findings and resolution links;
- final `audit_result` and rationale;
- proposed new baseline coordinates when `PASS`.

Evidence must be durable, access-controlled as needed, and content-hashed. Secrets, private provider
bodies, and unsafe raw tokens are excluded or sanitized without destroying the verification oracle.

## 7. Reruns and Candidate changes

- Retain all failed attempts. A later pass does not erase them.
- A deterministic failure followed by an unexplained retry is still a failure.
- Any source, lockfile, reference, generated asset, build configuration, or evidence-oracle change
  creates a new Candidate fingerprint.
- The auditor documents which prior evidence remains applicable and reruns everything reachable from
  the new delta. Identity/build and cross-cutting smoke always rerun.
- A failed audit cannot be “paper fixed” by editing the report; fix the Candidate/request/reference
  and issue a new audit revision.

## 8. Output decision example

```yaml
audit_id: FDA-2026-0042
change_id: [FCR-2026-0017]
previous_baseline_sha: <full-sha>
candidate_sha: <full-sha>
reference_version: UX_REFERENCE_V9
interaction_classification: 67/67
affected_scenes_passed: 2/2
required_tests_passed: 41/41
audit_result: PASS
```

This record is eligible for baseline promotion only if its coordinates exactly match the proposed
baseline manifest.
